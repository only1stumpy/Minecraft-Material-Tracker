# Antville Builder 2.0: production runbook

## Секреты и окружение Vercel

Для production нужны:

- DATABASE_URL — PostgreSQL URL из выбранного провайдера.
- BLOB_READ_WRITE_TOKEN — токен private Blob Store для прямой загрузки файлов.
- Node.js 22.12+ или 24.11+ для приложения. Для SQLite-импорта нужен Node.js 22.13+ или 24.11+ со встроенным модулем node:sqlite.

Задайте секреты в настройках проекта Vercel отдельно для Production и Preview. Не переносите их в Git, браузер или чат. Preview должен использовать отдельную тестовую базу и отдельное хранилище файлов. Сейчас переменные Preview указывают на тот же PostgreSQL, что и Production, поэтому `vercel.json` пропускает Preview-сборки. Не включайте их обратно, пока не подключите изолированную тестовую базу.

## Миграция и выпуск

1. Подготовьте отдельную копию production PostgreSQL и проверьте на ней восстановление.
2. Подключите к Vercel Preview отдельные тестовые PostgreSQL и Blob Store. Только после этого можно разрешить Preview-сборки.
3. Установите зависимости и проверьте схему: `npm ci`, `npx prisma validate`, `npm run typecheck`, `npm test`, `npm run lint`, `npm run build`.
4. Примените миграции к тестовой базе командой `npm run db:deploy`. Проверьте число карточек, материалы, файлы, роли и рабочие сценарии.
5. Перед изменением production создайте свежий backup и остановите запись старой версии.
6. Выпустите Production deployment. Его build command автоматически запускает `npm run db:deploy`, затем собирает приложение. Не запускайте эту команду локально через `vercel env run`: соединение к БД открывает среда сборки Vercel.
7. Проверьте `/api/health`, вход, создание/редактирование карточки, сбор материала, комментарии и скачивание приватной схемы.
8. Сверьте число карточек и агрегаты материалов с резервной копией. Оставьте старую версию и backup доступными до окончания проверки.

Не запускайте автоматическую генерацию reset-миграции на production. История Prisma migration должна содержать миграции, которые применяются командой db:deploy.

## Перенос SQLite

Если источник — SQLite, сохраните исходный файл отдельно и импортируйте его после применения миграций:

    npm run db:migrate:sqlite -- /absolute/path/to/dev.db

Импорт сохраняет ID, координаты, имена файлов, старый скриншот как legacy data URL, полный исходный JSON материалов и legacy checklist, если такая колонка есть. Валидные количества создаются как нормализованные материалы. Некорректные строки остаются в исходном снимке и попадают в ImportLog; процесс не подменяет их нулями.

Исходная SQLite хранит имена файлов схемы и материалов, но не сами байты `.litematic`/`.schem`/`.txt`/`.log`, поэтому их можно перенести только из отдельной копии, если она есть.

Импорт повторяемый: карточки с уже существующим ID пропускаются. Он не назначает владельца по догадке. В прежнем интерфейсе отметки «собрано» и «кто добыл» жили только в React state и не записывались в SQLite; восстановить их из базы невозможно. Если другой экспорт содержит сохранённый checklist, он переносится в legacyChecklist для ручной сверки, без автоматического связывания ника с аккаунтом.

## Резервные копии и восстановление

- Запускайте npm run db:backup до каждой миграции и по регулярному расписанию.
- Скрипт пишет PostgreSQL custom dump в каталог backups и проверяет, что архив читается через pg_restore. Если `DATABASE_URL` содержит Prisma-параметр `schema=public`, перед вызовом `pg_dump` скрипт удаляет только его; нативные параметры PostgreSQL, например `sslmode=require`, сохраняются. Некорректный или не-PostgreSQL URL отклоняется без вывода секрета.
- Переносите копии во внешнее зашифрованное хранилище; локальная папка backups исключена из Git и сама по себе не является резервированием.
- Включите резервирование/PITR у PostgreSQL-провайдера и задайте срок хранения, соответствующий сроку восстановления проекта.
- Не реже раза в месяц восстанавливайте копию в отдельную тестовую базу и проверяйте число пользователей, построек, материалов и вкладов.

### Подготовьте доступ к production

Команды ниже запускаются на вашем компьютере из корня клона. Нужны авторизованный Vercel CLI с доступом к проекту `antville` в scope `only1stumpys-projects`, Node.js с установленными зависимостями проекта, а также PostgreSQL client tools (`pg_dump`, `pg_restore`, `psql`). Проверьте вход и доступ к проекту:

```bash
npx vercel whoami
npx vercel project inspect antville --scope only1stumpys-projects
command -v pg_dump pg_restore psql
```

Синтаксис запуска команды с переменными без записи секретов на диск описан в [документации `vercel env`](https://vercel.com/docs/cli/env). Опции `--cwd`, `--scope` и `--project` описаны в [глобальных опциях Vercel CLI](https://vercel.com/docs/cli/global-options).

У компьютера должен быть прямой сетевой доступ к production PostgreSQL. Vercel CLI только передаёт production-переменные команде и не создаёт туннель к базе. Не используйте `vercel env pull`: скачивать секрет `DATABASE_URL` на диск не нужно.

### Создайте production backup

Перейдите в корень клона и запустите backup через Vercel. `env -u DATABASE_URL` убирает локальное значение, `--cwd /tmp` не даёт CLI читать `.env` из репозитория, а `env run` подставляет `DATABASE_URL` из Vercel Production. `BACKUP_DIRECTORY` указывает абсолютную папку, куда будет записан dump:

```bash
cd /absolute/path/to/Minecraft-Material-Tracker
mkdir -p "$PWD/backups"
env -u DATABASE_URL \
  npx vercel --cwd /tmp --scope only1stumpys-projects env run \
  --project antville -e production -- \
  env BACKUP_DIRECTORY="$PWD/backups" npm --prefix "$PWD" run db:backup
```

Команда выведет путь к проверенному файлу вроде `/absolute/path/to/Minecraft-Material-Tracker/backups/antville-20261014T120000Z.dump`. Сохраните этот путь для следующего шага. Не отправляйте его вместе с секретами в чат и не добавляйте dump в Git.

### Проверьте backup в отдельной базе

Сначала создайте у PostgreSQL-провайдера новую пустую базу, например `mmt-restore-check`. Команда восстановления не создаёт базу сама и откажется работать, если в ней уже есть пользовательские таблицы. Для этой команды укажите URL именно новой базы и абсолютный путь к dump из предыдущего шага:

```bash
cd /absolute/path/to/Minecraft-Material-Tracker
env -u DATABASE_URL \
  npx vercel --cwd /tmp --scope only1stumpys-projects env run \
  --project antville -e production -- \
  env \
    RESTORE_DATABASE_URL='postgresql://restore_user:password@db.example.com:5432/mmt-restore-check?sslmode=require' \
    RESTORE_TARGET_ISOLATED=YES \
    bash "$PWD/scripts/restore-database.sh" \
    "$PWD/backups/antville-20261014T120000Z.dump"
```

Внутри этой команды Vercel подставляет production `DATABASE_URL` только для проверки, что `RESTORE_DATABASE_URL` не указывает на ту же базу. Не убирайте внешний `env -u DATABASE_URL` и не запускайте скрипт обычной локальной командой: тогда проверка может использовать неправильный URL или отключиться. `RESTORE_DATABASE_URL` — адрес новой тестовой базы. Скопируйте обычный PostgreSQL URL из панели провайдера. Удалите из него только Prisma-параметры вроде `schema=public`: `psql` и `pg_restore` их не понимают. Нативные параметры PostgreSQL, например `sslmode=require`, оставьте. `RESTORE_TARGET_ISOLATED=YES` — явное подтверждение, что адрес ведёт в отдельную базу. Скрипт сравнивает host, эффективный порт и имя базы с production `DATABASE_URL` без учёта логина, пароля и query-параметров, отказывается от непустой базы, восстанавливает без владельцев и ACL, а затем проверяет наличие таблиц `Building`, `Material`, `User`.

Успешный результат выглядит так:

```text
Восстановление проверено: ключевые таблицы найдены
```

Если `db:restore` завершился ошибкой после начала восстановления, временная целевая база может содержать частичные объекты. Не запускайте повторную попытку в ней: удалите и заново создайте только эту изолированную временную базу, затем повторите команду. Production-базу для этого не удаляйте и не используйте.

После этого вручную проверьте вход, карточки, материалы и права пользователей. CI отдельно проверяет, что legacy-карточка пережила dump и restore; локальная ручная проверка нужна для данных и сценариев именно вашей копии. Удалите временную базу у PostgreSQL-провайдера и локальный dump, если они больше не нужны. Не переключайте production на восстановленную базу, пока эти проверки не пройдены.

При сбое сначала остановите запись в приложение. Восстанавливайте dump в отдельную базу, проверьте её и только затем переключайте `DATABASE_URL` в Vercel. Не восстанавливайте поверх единственной рабочей базы и не используйте существующую production-базу как `RESTORE_DATABASE_URL`. Резервирование базы не копирует объекты Blob: после восстановления отдельно проверьте наличие схем и скриншотов либо настройте нужный Blob Store.

## Наблюдаемость и доступность

- Настройте внешний uptime monitor на GET /api/health. Код ответа 200 означает, что приложение может выполнить запрос к базе; 503 означает недоступность БД.
- Проверяйте Function Logs и Observability Vercel после релиза и при росте 4xx/5xx. API возвращают безопасные сообщения без stack trace и секретов.
- Следите отдельно за PostgreSQL, Vercel Blob и сроком жизни резервных копий.
- Для V2 регион функций закреплён как `arn1` (Stockholm) по географическому предпочтению пользователя — ближе к России. Замеров из сетей игроков пока не было, поэтому локальные результаты после релиза служат только технической проверкой и не заменяют пользовательские замеры; см. раздел «Выбор региона».

### Realtime карточки

Карточка использует аутентифицированный SSE-маршрут `/api/buildings/[id]/events`. Сервер и обычный `/sync` получают cursor одним алгоритмом: учитываются обновление карточки, операции с материалами, комментарии и задачи. Новое SSE-событие содержит cursor, а клиент вызывает `router.refresh()` только после его сдвига.

Поток живёт ограниченное окно 25 секунд (`maxDuration = 30` для Vercel Function), отправляет heartbeat-комментарии и закрывается сам, чтобы `EventSource` переподключился с `Last-Event-ID`. При переходе вкладки в фон соединение закрывается и открывается заново при возврате. Новый поток повторно проверяет сессию, временный пароль и существование карточки; `since` и `Last-Event-ID` не дают пропустить изменения при переподключении.

Это SSE поверх Vercel Functions, отдельный WebSocket-сервис не используется. Открытая вкладка держит Function invocation и создаёт периодические запросы cursor к PostgreSQL, поэтому при большом числе одновременных карточек контролируйте длительность функций, лимиты и стоимость Vercel, а также нагрузку базы.

### Выбор региона

Vercel указывает iad1 (Washington, D.C.) как регион функций по умолчанию и рекомендует располагать функцию рядом с базой. Для V2 выбран `arn1` (Stockholm): пользователь попросил регион между целевыми территориями и ближе к России. Это географический выбор без замеров из сетей игроков. Поддерживаемые регионы и способ настройки описаны в [списке регионов Vercel](https://vercel.com/docs/regions) и [настройке региона функций](https://vercel.com/docs/functions/configuring-functions/region).

Порядок:

1. После production-деплоя запросите `https://antville.vercel.app/api/health` и убедитесь, что ответ HTTP 200. Проверьте заголовок `x-vercel-id`: в сокращённом примере `fra1::arn1::…` первый регион (`fra1`) — предыдущий регион на пути запроса, а второй (`arn1`) — регион, где фактически выполняется функция. Не публикуйте полный заголовок или уникальный ID запроса.
2. С текущего хоста проверьте полный HTTPS-запрос и задержку, например: `curl -sS -o /dev/null -D - -w '\nlatency=%{time_total}s\n' https://antville.vercel.app/api/health`. Повторите запрос несколько раз и запишите дату, статус, `x-vercel-id` и результаты.
3. Этот замер показывает путь только от текущего хоста до Vercel и не является репрезентативным замером сетей игроков в России и Приднестровье. Для настоящего сравнения запустите `npm run region:measure` из нескольких реальных сетей, когда появится отдельный Preview с тестовой базой.
4. Храните PostgreSQL рядом с функциями. Если перемещение БД невозможно, отдельно измерьте фактическую пару «игрок → функция → БД» и пересмотрите выбор региона по p95.

Регион `arn1` выбран по географическому предпочтению пользователя; фактических сетевых замеров из рабочих мест игроков пока нет. После каждого production-деплоя фиксируйте `x-vercel-id`, результат `/api/health` и задержку с текущего хоста отдельно от будущих пользовательских замеров.

Фактическая проверка 14 октября 2026 года: GET `https://antville.vercel.app/api/health` вернул HTTP 200 и `{"status":"ok"}`; сокращённая цепочка `x-vercel-id` имела вид `fra1::arn1::…`, то есть функция выполнялась в `arn1`. Один запрос с текущего хоста занял 1.286603 секунды (округлённо 1.29 секунды). Egress этого хоста проходит через proxy, поэтому это техническая проверка production-маршрута, а не замер из сети игрока. Полный заголовок и уникальный ID запроса не публикуются.

## Добавление модератора в production

Если сайт работает, выдайте роль через `/admin`: найдите игрока и выберите `MODERATOR` либо создайте аккаунт сразу с этой ролью. Для аварийного CLI-пути используйте только [подробную инструкцию для production](production-moderator.md).

Не запускайте здесь сокращённую команду `vercel env run`: локальный `.env` или экспортированный `DATABASE_URL` может направить скрипт не в production. Подробная инструкция очищает локальное окружение, задаёт production-проект явно и объясняет, как проверить результат и откатить роль.

## Откат релиза

Откат кода и откат схемы — разные операции. Сначала переключите домен на предыдущий совместимый deployment. Не пытайтесь автоматически отменить расширяющую миграцию, которая уже приняла новые записи. Если возврат к старой схеме необходим, остановите запись, восстановите согласованный backup в отдельную базу и переключите приложение только после проверки.
