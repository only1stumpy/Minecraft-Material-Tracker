# Выпуск и восстановление Minecraft Material Tracker (MMT)

Эта памятка предназначена владельцам и сопровождающим MMT. Здесь описаны выпуск версии 2.0, резервное копирование, проверка восстановления и действия при сбое. В документе нет адресов баз данных, имён аккаунтов и значений секретных ключей. Секреты настраиваются в Vercel, у провайдера PostgreSQL и в Vercel Blob.

## Что нужно подготовить

Для рабочего окружения нужны:

- `DATABASE_URL` — адрес базы PostgreSQL;
- `BLOB_READ_WRITE_TOKEN` — закрытый токен чтения и записи Vercel Blob для схем, скриншотов и списков материалов;
- Node.js 22.12+ или 24.11+;
- утилиты клиента PostgreSQL: `pg_dump`, `pg_restore` и `psql` — для резервных копий и проверки восстановления.

Задайте секреты в Vercel отдельно для рабочей среды (`Production`) и среды предварительного просмотра (`Preview`). Не переносите их в Git, сообщения, скриншоты, документацию или историю команд. Рабочая, тестовая и локальная копии должны использовать разные базы и разные хранилища файлов.

Сейчас переменные среды предварительного просмотра указывают на ту же базу PostgreSQL, что и рабочая среда, поэтому `vercel.json` пропускает такие сборки. Не включайте сборки `Preview`, пока не подключите отдельную тестовую базу и отдельное тестовое хранилище Blob.

## Выпуск версии 2.0

Версия 2.0 начинается с новой схемы PostgreSQL. Обычный выпуск V2 не переносит старую SQLite-базу, не сверяет с ней количество записей и не требует останавливать прежнюю версию. Не запускайте сброс базы и не создавайте вручную миграции для сброса в рабочем окружении.

### Предварительная проверка

1. Убедитесь, что проверки CI прошли на том изменении, которое собираетесь выпустить.
2. Проверьте, что резервная копия базы и загруженных файлов свежая и доступна владельцу сервиса.
3. Подключите к `Preview` отдельную пустую базу PostgreSQL и отдельное хранилище Blob. Только после этого разрешайте сборки предпросмотра.
4. Установите зависимости и проверьте проект:

   ```bash
   npm ci
   npx prisma validate
   npm run typecheck
   npm test
   npm run lint
   npm run build
   ```

5. Примените миграции к изолированной базе предварительного просмотра:

   ```bash
   npm run db:deploy
   ```

6. Загрузите в `Preview` только тестовые данные. Проверьте карточки построек, материалы, файлы, роли и основные рабочие сценарии.

### Выпуск в рабочую среду

1. Перед первой миграцией схемы в рабочей среде создайте свежую резервную копию PostgreSQL и убедитесь, что архив читается.
2. Выпустите рабочее развёртывание в Vercel. Команда сборки из `vercel.json` сначала запускает `npm run db:deploy`, затем собирает приложение.
3. Не запускайте `npm run db:deploy` локально через `vercel env run`: миграции рабочей базы выполняет среда сборки Vercel.
4. После выпуска проверьте `/api/health`, вход, создание и редактирование карточки, взятие материала в работу, комментарии, уведомления и скачивание закрытой схемы.
5. Сохраните свежую копию базы и результат ручной проверки до завершения выпуска.

В историю миграций Prisma должны попадать только миграции из репозитория. Не запускайте автоматическую миграцию для сброса в рабочей среде. Не подключайте старую SQLite-базу к V2 и не используйте `db:migrate:sqlite` как часть обычного выпуска. Отдельный перенос возможен только по самостоятельному плану владельца, с отдельной копией и проверкой в изолированной среде.

## Отдельная среда предпросмотра

Среда предварительного просмотра (`Preview`) нужна для проверки новой версии до изменения рабочего сервиса. Для неё должны быть:

- отдельная база PostgreSQL;
- отдельное хранилище Vercel Blob;
- отдельные значения `DATABASE_URL` и `BLOB_READ_WRITE_TOKEN`;
- тестовые данные вместо копии рабочих секретов и файлов.

Не направляйте `Preview` на рабочую базу или рабочее хранилище Vercel Blob. Не включайте эти сборки только ради удобства: сначала подключите изолированные ресурсы, затем проверьте миграции и сценарии.

## Резервные копии PostgreSQL

База данных и прикреплённые файлы — две разные части данных. Копия базы не содержит схемы и скриншоты из Blob, а копия Blob не содержит пользователей, карточки и материалы.

- Запускайте `npm run db:backup` перед каждой миграцией и по расписанию.
- Скрипт создаёт дамп PostgreSQL в формате `custom` в каталоге `backups` и проверяет его через `pg_restore --list`.
- Если `DATABASE_URL` содержит параметр Prisma `schema=public`, скрипт удаляет только этот параметр перед вызовом `pg_dump`. Остальные параметры PostgreSQL, например `sslmode=require`, сохраняются.
- Некорректный или не-PostgreSQL URL скрипт отклоняет без вывода секрета.
- Локальный каталог `backups` исключён из Git и сам по себе не является резервированием. Переносите копии во внешнее зашифрованное хранилище.
- Включите резервирование и PITR (восстановление на момент времени) у провайдера PostgreSQL. Срок хранения должен соответствовать времени, за которое сервис нужно восстановить.
- Не реже раза в месяц восстанавливайте копию в новую пустую тестовую базу. Проверяйте вход, карточки, материалы, вклад участников и доступ к схемам и изображениям.

Ограничьте доступ к копиям владельцами, которым он нужен для восстановления. Записывайте дату проверки, тип восстановленных данных и результат. Не публикуйте сами копии, ссылки на них или значения секретов.

### Подготовьте доступ к рабочему проекту

Команды ниже запускаются на вашем компьютере из корня клона. Нужны авторизованный Vercel CLI с доступом к проекту, Node.js с установленными зависимостями и утилиты клиента PostgreSQL:

```bash
npx vercel whoami
npx vercel project inspect antville --scope only1stumpys-projects
command -v pg_dump pg_restore psql
```

Если имя проекта или команда Vercel отличаются, подставьте значения из панели своего проекта. Синтаксис `vercel env run` описан в [документации Vercel CLI](https://vercel.com/docs/cli/env), а общие параметры CLI — в [документации глобальных параметров Vercel](https://vercel.com/docs/cli/global-options).

У компьютера должен быть прямой сетевой доступ к рабочей базе PostgreSQL. Vercel CLI передаёт переменные команде, но не создаёт туннель к базе. Не используйте `vercel env pull`: скачивать `DATABASE_URL` на диск не нужно.

### Создайте копию рабочей базы

Перейдите в корень клона и выполните:

```bash
cd /absolute/path/to/Minecraft-Material-Tracker
mkdir -p "$PWD/backups"
env -u DATABASE_URL \
  npx vercel --cwd /tmp --scope only1stumpys-projects env run \
  --project antville -e production -- \
  env BACKUP_DIRECTORY="$PWD/backups" npm --prefix "$PWD" run db:backup
```

Команда выведет путь к проверенному файлу вида `/absolute/path/to/Minecraft-Material-Tracker/backups/antville-20261014T120000Z.dump`. Сохраните этот путь для проверки восстановления. Не отправляйте его вместе с секретами в чат и не добавляйте дамп в Git.

### Проверьте восстановление в новой изолированной базе

Восстановление проверяется только в новой пустой базе. Сначала создайте у провайдера PostgreSQL отдельную базу, например `mmt-restore-check`. Скрипт не создаёт базу сам и откажется работать, если в ней уже есть пользовательские таблицы.

Укажите URL именно этой новой базы и путь к дампу:

```bash
cd /absolute/path/to/Minecraft-Material-Tracker
env -u DATABASE_URL \
  npx vercel --cwd /tmp --scope only1stumpys-projects env run \
  --project antville -e production -- \
  env \
    RESTORE_DATABASE_URL='postgresql://restore_user:password@db.example.com:5432/mmt-restore-check?sslmode=require' \
    RESTORE_TARGET_ISOLATED=YES \
    bash "$PWD/scripts/restore-database.sh" \
    "$PWD/backups/antville-20261014T120000Z.dump"
```

Вместо примера укажите настоящий URL новой базы. Не публикуйте его: в нём могут быть логин и пароль. Удалите из URL только Prisma-параметры вроде `schema=public`, которые не понимают `psql` и `pg_restore`; параметры PostgreSQL, например `sslmode=require`, оставьте.

`RESTORE_TARGET_ISOLATED=YES` — обязательное подтверждение, что адрес ведёт в отдельную базу. Скрипт сравнивает host, порт и имя базы с рабочим `DATABASE_URL`, отказывается от совпадения и непустой базы, восстанавливает без владельцев и ACL, а затем проверяет таблицы `Building`, `Material` и `User`.

Успешный результат:

```text
Восстановление проверено: ключевые таблицы найдены
```

Если восстановление началось и завершилось ошибкой, временная база может содержать частичные объекты. Не повторяйте команду в ней: удалите и заново создайте только эту изолированную временную базу. Рабочую базу не удаляйте и не используйте как `RESTORE_DATABASE_URL`.

После проверки вручную проверьте вход, карточки, материалы и права пользователей. Удалите временную базу и локальный дамп, когда они больше не нужны. Не переключайте приложение на восстановленную базу, пока проверка не пройдена.

Если рабочий сервис повреждён, сначала остановите запись в приложение. Восстановите архив в отдельную базу, проверьте её и только затем переключайте `DATABASE_URL` в Vercel. Резервная копия базы не возвращает файлы Blob — их проверяют и восстанавливают отдельной процедурой.

## Снимок Vercel Blob

Для схем, скриншотов и списков материалов используется отдельная копия Blob. Команда `npm run blob:backup` постранично читает закрытое хранилище Blob, сохраняет файлы и `manifest.json`, а для каждого объекта записывает размер, тип, дату, `etag` и SHA-256. Команда не удаляет объекты из хранилища Blob.

Для операции нужны доступ к проекту Vercel, установленные зависимости и свободное место под файлы. Токен `BLOB_READ_WRITE_TOKEN` берётся из рабочей среды Vercel только на время команды. Прямой доступ к Blob идёт с вашего компьютера; `vercel env run` не создаёт сетевой туннель.

Создайте снимок:

```bash
cd /absolute/path/to/Minecraft-Material-Tracker
env -u BLOB_READ_WRITE_TOKEN \
  npx vercel --cwd /tmp --scope only1stumpys-projects env run \
  --project antville -e production -- \
  npm --prefix "$PWD" run blob:backup -- \
  "$PWD/backups/blob-snapshots/antville-20261014T120000Z"
```

Успешный вывод:

```text
Создан snapshot Blob: /absolute/path/to/Minecraft-Material-Tracker/backups/blob-snapshots/antville-20261014T120000Z (N объектов)
```

Проверьте наличие `manifest.json` и сохраните весь каталог с закрытыми правами. Снимок создаётся с правами `0700`, манифест — `0600`, файлы — `0600`; это защита локального каталога, а не шифрование. Перенесите снимок во внешнее зашифрованное хранилище с отдельными учётными данными. Не добавляйте его в Git, не храните единственную копию рядом с приложением и не складывайте её в то же хранилище Blob.

Расписание в проекте не настроено автоматически. Для рабочего сервиса заведите как минимум ежедневную копию базы и Blob, дополнительную копию перед каждой миграцией и ежемесячную проверку восстановления в изолированной среде.

## Восстановление Vercel Blob

Проверяйте восстановление в отдельном новом хранилище Blob. Сначала скачайте снимок из внешнего хранилища и убедитесь, что это закрытый каталог с исходным `manifest.json`. Токен целевого хранилища задайте через защищённую переменную `TARGET_BLOB_READ_WRITE_TOKEN`; не записывайте его в `.env` репозитория и не отправляйте в чат.

```bash
cd /absolute/path/to/Minecraft-Material-Tracker
export TARGET_BLOB_READ_WRITE_TOKEN='токен отдельного тестового хранилища Blob'
env -u BLOB_READ_WRITE_TOKEN \
  npx vercel --cwd /tmp --scope only1stumpys-projects env run \
  --project antville -e production -- \
  env BLOB_READ_WRITE_TOKEN="$TARGET_BLOB_READ_WRITE_TOKEN" \
  npm --prefix "$PWD" run blob:restore -- \
  "$PWD/backups/blob-snapshots/antville-20261014T120000Z"
```

Команда сначала проверяет манифест, безопасные пути, права файлов, размеры и SHA-256. Существующий объект оставляется на месте только при полном совпадении байтов. Отсутствующие объекты загружаются с `allowOverwrite=false`, поэтому команда не удаляет и не перезаписывает чужие файлы.

После восстановления сравните `manifest.json` с объектами целевого хранилища и отдельно проверьте открытие схемы, скриншота и списка материалов из карточки. Не переключайте приложение на новое хранилище Blob, пока проверка не пройдена и не создана новая копия базы.

В аварийной ситуации восстановление в рабочее хранилище Blob выполняйте только после остановки записи и решения владельца сервиса. Сначала проверьте снимок в отдельном хранилище. Не используйте единственное рабочее хранилище как место для эксперимента.

## Наблюдаемость и доступность

- Настройте внешний монитор доступности на `GET /api/health`. Ответ `200` означает, что приложение смогло выполнить запрос к базе; ответ `503` означает недоступность базы.
- После выпуска и при росте ответов `4xx/5xx` просматривайте журналы функций и раздел Observability в Vercel. API не должны отдавать трассировку стека и секреты.
- Следите отдельно за PostgreSQL, Vercel Blob и сроком хранения резервных копий.
- Если проверка доступности не проходит, сначала проверьте статус базы, значения переменных Vercel и последнее развёртывание. Не публикуйте URL базы и секреты в отчёте.

## События карточки в реальном времени

Карточка использует защищённый поток событий от сервера (SSE) по адресу `/api/buildings/[id]/events`. Серверный маршрут и обычный `/sync` одинаково определяют последнее изменение: учитываются карточка, материалы, комментарии и задачи. Новое событие содержит отметку этого изменения, а клиент вызывает `router.refresh()` только после её сдвига.

Поток работает ограниченное время — 25 секунд при `maxDuration = 30` для функции Vercel. Он отправляет служебные сообщения, подтверждающие работу соединения, и закрывается сам, чтобы `EventSource` подключился заново с `Last-Event-ID`. Когда вкладка уходит в фон, соединение закрывается и открывается снова при возвращении. Новый поток заново проверяет сессию, временный пароль и существование карточки; `since` и `Last-Event-ID` помогают не пропустить изменения при переподключении.

Это SSE через функции Vercel, отдельный WebSocket-сервис не используется. Открытая вкладка удерживает вызов функции и периодически проверяет последние изменения в PostgreSQL. При большом числе одновременных карточек контролируйте длительность функций, лимиты и стоимость Vercel, а также нагрузку базы.

## Выбор региона

Для V2 в `vercel.json` закреплён регион функций `arn1` (Стокгольм). Он выбран по географическому предпочтению пользователя как вариант ближе к России. Это не подтверждает задержку из сетей игроков: рабочих замеров из России и Приднестровья пока нет.

Vercel указывает `iad1` (Вашингтон) как регион функций по умолчанию и рекомендует размещать функцию рядом с базой. Поддерживаемые регионы описаны в [списке регионов Vercel](https://vercel.com/docs/regions), настройка функций — в [документации настройки региона](https://vercel.com/docs/functions/configuring-functions/region).

Порядок измерения:

1. После рабочего развёртывания запросите `https://antville.vercel.app/api/health` и убедитесь, что ответ HTTP 200.
2. Проверьте заголовок `x-vercel-id`. В сокращённой цепочке вида `fra1::arn1::…` первый регион (`fra1`) — предыдущий узел пути запроса, второй (`arn1`) — регион выполнения функции. Полный заголовок и уникальный ID запроса не публикуйте.
3. С текущего компьютера измерьте несколько запросов:

   ```bash
   curl -sS -o /dev/null -D - -w '\nlatency=%{time_total}s\n' https://antville.vercel.app/api/health
   ```

4. Для сравнения двух регионов предпросмотра используйте из нескольких реальных сетей игроков:

   ```bash
   npm run region:measure -- fra1=https://preview-fra.example/api/health arn1=https://preview-arn.example/api/health
   ```

   Скрипт делает 20 измерений каждого адреса, отбрасывает первые два и выводит медиану и p95 полного HTTPS-запроса.

5. Откройте панель провайдера PostgreSQL и проверьте поле `Region`. Пока регион базы не сверен, требование близкого размещения базы и функций не считайте выполненным.
6. Если переместить базу нельзя, измерьте фактический путь «игрок → функция → база» и пересмотрите регион по p95.

Замер с одного компьютера показывает только маршрут этой сети и не заменяет замеры игроков. Не публикуйте имя узла, `DATABASE_URL` и другие учётные данные.

## Выдача роли модератора

Если сайт работает, выдайте роль через `/admin`: найдите игрока и выберите `MODERATOR` либо создайте аккаунт сразу с этой ролью. Подробный порядок описан в [инструкции выдачи модератора](production-moderator.md).

Для аварийного CLI-пути используйте только указанную инструкцию. Не запускайте здесь сокращённую команду `vercel env run`: локальный `.env` или экспортированный `DATABASE_URL` может направить скрипт не в рабочую базу. Перед изменением роли ещё раз сверьте Minecraft-ник и выбранный Vercel-проект.

## Откат выпуска

Откат кода и откат схемы — разные операции.

1. При ошибке приложения остановите изменения данных, если это возможно, и проверьте журналы Vercel.
2. Для отката кода переключите домен на предыдущее совместимое развёртывание через Vercel.
3. Не пытайтесь автоматически отменить расширяющую миграцию, которая уже приняла новые записи.
4. Если нужна старая схема, остановите запись, восстановите согласованную копию в отдельную базу и проверьте её.
5. Переключайте `DATABASE_URL` только после проверки восстановленной базы и согласования владельца сервиса.
6. После восстановления снова включите резервное копирование и проверьте следующий снимок.

Не восстанавливайте резервную копию поверх единственной рабочей базы. Не переключайте сервис на непроверенную копию. Восстановление PostgreSQL и восстановление Blob выполняются отдельно и должны быть проверены вместе.
